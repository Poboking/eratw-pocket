## 0. 防眼瞎清单（十条，逐条有代码锚点）

1. **字号档位不是「只改字号」，是逻辑列宽。** `fontColumnsOverride` 在 `CanvasConsoleView` 构造期派生 metrics/paints（`MainActivity.kt:138-145`），同一列数经 `screen.clientWidth` 变成 `GameSession.consoleWidth`（`GameHost.kt:1148`），还喂给脚本像素尺度 `fontSizePx = metrics.fontSizePx`（`GameHost.kt:1159`）。⇒ 竖屏档位必须**按方向在装配期选档**，语义 = 原版改窗口宽度，不是 CSS 缩放。
2. **改档生效走 `recreate()`，不要发明热切换。** 现有机制：设置页改档 → `onActivityResult` 比较 `appliedFontColumns` → 变了就 `recreate()`（`MainActivity.kt:201-206`、`:257`）。竖屏档沿用同口径。
3. **禁止在 app 层给控制台 canvas 做文字回折。** 渲染侧是列几何模型（按钮有 `lineSerial/startCol/endCol`，`ConsoleOptions.kt:39`），回折会破坏按钮命中、与 E2E golden 610 行对拍。正文区阶段一 = `CanvasConsoleView` **原样嵌入**（原型里的「回折 chips」是概念演示，见 §4.2）。
4. **禁止硬编码指令号→名称映射**（310=摸屁股 是语料内容，会漂）。指令盘数据唯一来源 = `GameHost.currentOptions()` 快照（`GameHost.kt:616-621`），分组复用 `railRowsOf` 按屏行分行（`ShellUi.kt:212-224`）。
5. **禁止硬编码 HUD 数值。** M1 数值条走「行解析、失配即隐藏」，M2 走 VM 只读快照（§4.1）。解析不到就降级成无数值 HUD，**绝不显示编造的默认值**。
6. **锁横屏现状与理由必须知道再动手。** `AndroidManifest.xml:22` `screenOrientation="sensorLandscape"`，注释写明理由（PC 基准 199 列版面复刻）。本设计**接受版面分叉**换竖屏可玩性（用户 2026-10-27 指令），横屏行为完全不变（§6）。
7. **不要简化输入条的自动收起逻辑。** 15s 静置收起、输入法组合态（有焦点不收）的豁免是踩过坑的（拼音候选不上屏不改文本），在 `ShellUi.kt:300-307`。沿用，不重写。
8. **手势单入口教训。** `InputKnob` 曾因 clickable+draggable+verticalDrag 三者抢同一个 down 导致「点抓手没反应」（`ShellUi.kt:612-676` 注释）。竖屏新增任何可拖控件一律单 `awaitEachGesture` 分流。
9. **性能红线：UI 轮询路径禁正则。** chips 每 250ms 扫描刷新已是现状（`ShellUi.kt:358-360` 注释）；HUD 行解析若进轮询，频率 ≤ 扫描频率、实现用 `indexOf`/手写扫描（FINDELEMENT 的 Android ICU 正则坑在案，BOARD 2026-10-23）。
10. **不碰 core-vm / render 语义面。** 本设计全部落在 app 壳层 + manifest + UiPrefs。render 的 `ScreenLayout` 是**只读复用**（§5），不是修改对象。E2E golden（610 行）零影响——验收时跑一遍证明它。
11. **「屏幕形态」是壳层摆法分级，不是页面导航，更不是引擎状态机。** 竖屏壳按当前屏快照分 G0 菜单 / G1 探索 / G2 单人 / G3 多人四级（§3.5、§3.6），判据只有候选列表 + 行解析出的角色块数，**禁止**：给 core-vm 加「当前场景」概念、按形态切数据源、用正则识别「菜单/探索」语义词。误分级的最坏后果 = 指令盘多展开一次或多显示一条角色条，零语义影响。
12. **绝不替游戏做「换交互对象」。** G3 的角色条/立绘点击只切**壳层显示上下文**（HUD 数值行、抽屉标题、高亮），一字节都不提交。游戏内换对象是 `变更对象[802]` 这个游戏自己的按钮，壳层只负责让它可点。理由不是洁癖：BOARD 2026-10-25 真机红例「输入值跨屏错位」（`角色变量 CFLAG 第 1 参数 200 越界`）就是壳层替游戏交了一个它没资格交的值。
13. **立绘上限 10 是原版事实，不改。** 舞台按人数自适应宽度（§3.6.3 常量表），10 人同屏允许横滑，**禁止**改成「只显示最近 N 个」或「分页」——玩家需要看到全场谁在。分页会隐藏在场者，是产品级错误。
14. **壳内尺寸一律用「相对宿主容器」的百分比 / dp，禁止视口单位。** `vh`/`vw` 是**浏览器视口**（或 Android 的 window）尺寸，与「壳层分区占多少」无关；原型第一版指令盘展开用了 `max-height:34vh`，在 1500px 高的预览窗口里算出 510px，把手机框（844px）的收起按钮顶出框外 ⇒ 玩家看到的症状是「**指令盘无法收起**」（2026-10-27 用户实测报告）。Compose 侧同理：用 `BoxWithConstraints` 的 `maxHeight` 派生，不要用 `LocalConfiguration.screenHeightDp` 直接乘系数。
15. **承载分区的固定框不可被程序滚动。** 隐藏态控件若用 `translateY(102%)` 滑出底边，**变换后的盒子会计入 scrollable overflow**，把容器 `scrollHeight` 撑大（实测 +92px）；此后任何 click/focus 都会触发框内滚动，把 HUD 顶出可视区（呈现为「HUD 缺一截」「顶部内容莫名消失」）。原型用 `overflow: clip`（不创建滚动容器、`scrollTop` 恒 0）修掉；Compose 里对应「不要给固定高度的 Column 套 `verticalScroll`」，隐藏控件用 `AnimatedVisibility` 真正移除而不是位移。
16. **同一游戏界面 → 同一壳层形态。** G2（单人）与 G3（多人）在横屏是同一个界面，只差立绘数量，**必须共用同一套 HUD 骨架与同一个渲染函数**，差别只允许「多一条角色条」（§3.6.1）。不许因为「数据形状不同 / 内容多少不同」就换一套 HUD——那会让玩家觉得进了另一个页面。判断标准：**横屏截图里的分区结构相同 = 竖屏壳结构必须相同**。
17. **HUD 只显示「当前主体」，不并列堆主角+少女。** 角色态只放少女的 6 条，主角态只放主角的 6 条；主体切换是壳层状态，不落盘、不提交指令。M1 早期版本曾用「主角行 + 角色行」双行并列，实测在小屏把正文压到 34% 且信息重复，已废弃。

## 1. 背景与现状

### 1.1 现在为什么是横屏

`MainActivity` 锁 `sensorLandscape`（`AndroidManifest.xml:22`），理由（manifest 注释原文概括）：eratw 是 PC 基准横屏版面（WindowX 1800px / 199 列），竖屏下屏宽减半，字号反推出的列数掉档、折行与素材尺寸全部与原版分叉。锁横屏后按屏宽反推即复刻原版版面；`configChanges` 已吞掉旋转不重建 Activity。

### 1.3 本设计与「版面复刻」的关系

竖屏不是替换横屏，是**新增一条版面路径**：横屏（含锁横屏偏好）走现有代码零改动；竖屏走新壳。用户已在 2026-10-27 定调「要适合安卓手机的竖屏布局」，可玩性优先于版面 1:1 复刻；原版面诉求由 §6 的「锁横屏」方向偏好保留。

## 2. 目标与非目标

**目标（阶段一，本契约交付面）**
1. 解锁屏幕方向（跟随系统，缺省），横屏行为与现状逐字节一致。
2. 竖屏三区壳：顶部状态 HUD（可展开状态详情抽屉）、中部正文（canvas 原样）、底部指令盘（可展开全部指令）。
3. **四形态壳层分级 G0/G1/G2/G3**（§3.5、§3.6）：起床菜单页 / 日常探索页 / 单人交互页 / 多角色交互页同一壳、四种摆法，判据纯壳层。
4. 多角色支持（§3.6）：在场角色条（横滑，上限 10）、主角 + 当前角色双行数值、立绘舞台可折叠、详情按角色分节。**换对象仍走游戏自己的 `变更对象[802]`。**
4. 竖屏字号档位（50/62/75/90 列，缺省 62），与横屏档位互相独立、按方向在装配期选择。
5. 输入条 / 抓手 / 宏 / 长按提示 / 加载与失败覆盖层：横竖屏共用现有实现。
6. 断点自适应（§5）：HUD 条数、指令盘列数、抽屉列数按屏宽分档。

**非目标（明确不做，防跑偏）**
- ❌ 控制台文字回折 / 结构化行抽取为 Compose 控件（阶段二，跨模块另立波次，涉 render 行模型）。
- ❌ HUD 数值的 VM 变量快照接口（阶段二，涉 core-vm 面 + VM 线程模型；M1 用行解析降级方案）。
- ❌ 平板/折叠屏双栏（左正文右指令）布局（阶段二）。
- ❌ 立绘/图片的壳层重绘——canvas 已渲染图片行（BOARD 2026-10-26：立绘图片行几何已落 render），竖屏原样保留。
- ❌ 语义级指令分组标签的自动识别（阶段二；M1 指令盘按屏行平铺 + 收起态 peek 首行）。

### 3.5 屏幕形态分级 G0 / G1 / G2 / G3（竖屏壳层的核心适应机制）

eratw 实际游戏流里有四种屏面（用户 2026-10-27 提供的四张截图钉死）：**开局起床菜单页**（图1：黄字提示 + 主菜单/系统菜单两段编号指令大列表）、**日常探索页**（图2：点「睁开眼睛」后的常规布局，短正文 + Act/Ex 指令组）、**单人角色交互页**（图0：遇到一位美少女，第一版原型已做）、**多角色交互页**（图3：同时遇到 2~10 位，立绘并排、每条数值按角色分行、Palam 只显示当前对象）。四者的共同点是**同一引擎屏**（同一个 canvas 快照 + 同一个 options 快照），差别只在内容形状。竖屏壳不做页面导航，按快照形状分级摆：

| 形态 | 判据（M1，纯壳层） | HUD | 指令盘 | 正文 / 立绘 |
|---|---|---|---|---|
| **G0 菜单页** | `options.size ≥ 16`（睁眼前主菜单实测 27 钮） | G1 级徽章（地点/时间入徽章、所持金入名字行），无 Palam 抽屉 | **自动展开** + 组标签（【主菜单】/【系统菜单】） | 通常只有几行提示，中段自然留白 |
| **G1 探索页** | `options.size < 16` 且**不含 3xx 编号**候选 | 徽章级（buff 行 `[调和魔药]…` 整行变 chips） | 收起态 peek（首行 ≤4 枚）+ 组标签（Act/Ex） | Status 行 + Look 行 + 描述，量少 |
| **G2 单人交互页** | 含 3xx，且解析出 **1 个**角色块 | **统一 HUD**（§3.6.1）：当前少女的数值条 + Palam 抽屉；可切主角 HUD | 收起态 peek，3xx 亲密组排最前 | 叙事文本流 + 立绘（canvas 流内） |
| **G3 多角色交互页**（§3.6） | 含 3xx，且解析出 **≥2 个**角色块（或候选含 `变更对象[802]`） | **与 G2 完全同一套 HUD**，只多一条角色条（§3.6.1） | 同上；`变更对象[802]` 在系统组（不特殊置顶） | 叙事 + **独立立绘舞台**（≤10 张横滑，可折叠） |

判据实现（纯函数，放 `PortraitGrid.kt`）：

```kotlin
enum class TrayForm { MENU, EXPLORE, INTERACT, MULTI }

/** @param charCount 从屏行解析出的角色块数（`[名字]` 行 + 其后的 好感度 行），解析不出传 0 */
fun trayFormOf(options: List<ConsoleOption>, charCount: Int): TrayForm = when {
    options.any { it.number in 300..399 } ->
        if (charCount >= 2 || options.any { it.number == 802 }) TrayForm.MULTI else TrayForm.INTERACT
    options.size >= 16 -> TrayForm.MENU
    else               -> TrayForm.EXPLORE
}
```

（`number` = 从候选 label 剥出的 `[数字]`；`ConsoleOption` 没有 number 字段时在壳层剥一次。**顺序先判 3xx**：交互页候选也可能 >16 枚，但含 3xx 永远优先归 G2/G3。`802` 是原版多角色时的目标切换按钮，作为角色块解析失败时的兜底判据——只读候选编号，不做语义推断。）

**组标签**（M1）：`DisplayLine.serial` 与 `ConsoleOption.lineSerial` 是同一序号体系（`LineBufferConsoleSink.kt:280` 注释明示「右侧选项栏用它切当前页」）。取候选首末 `lineSerial` 区间内的 `lines()` 屏行（`LineBufferConsoleSink.kt:398`），行文本**整行命中** `【…】` 全角括号模式（手写 `indexOf('【')`/`endsWith('】')`，禁正则）→ 作为该屏行分组的组头标签；剥不出 → 组标签缺省、按钮照常平铺（形态判据不受影响）。

**指令盘随形态的展开默认**：G0 = 展开（候选多、正文短，展开是用户的下一步）；G1/G2/G3 = peek 收起（正文优先）。用户的「更多指令」开关只作用于当前屏（跨屏不记忆），`command_tray_open` 偏好只记 G1/G2/G3 的用户手动偏好，G0 的自动展开不受它影响。

**误分级零成本**：分级只决定壳层摆法（HUD 显隐抽屉、角色条显隐、盘开合、组头），数据源、命中、提交路径完全同一份。判据边界（8~16 钮的存档页、无 3xx 的训练页）落 G1 是可接受摆法。

### 3.6 G3 多角色交互页（图3：同时遇到 2~10 位少女）

**场景事实**（用户图3 钉死）：原版在这种屏面里
- 顶部数值按角色分行：`昂`（主角）一行、`白莲` 一行，各带体力/气力/法力/酒/精；
- `[白莲] [同行中] [一轮]` 一行列出在场角色；
- `Palam` 段**只显示当前交互对象**（图3 是白莲）；
- 立绘并排（图3 两张，**上限 10 张**）；
- 候选里多出 `变更对象[802]`——原版用它换交互对象。

**竖屏壳的四件事**：① 角色条标注在场谁是谁；② 数值行区分「主角 / 当前角色」；③ 立绘有独立可折叠的舞台，最多吃 10 张；④ **换对象仍走游戏自己的 `变更对象[802]`**。

#### 3.6.1 统一 HUD（G2 与 G3 同一套，本节是唯一规格）

**原则（2026-10-27 用户定调）**：单人交互页与多角色交互页在横屏是**同一个游戏界面**，只差立绘数量。所以壳层**必须是同一套 HUD**，差别只允许「多一条角色条」。不许因为数据形状不同就换一套 HUD —— 那会让玩家觉得进了另一个页面。

**骨架**（从上到下，两页共用；HTML 一份、`renderHud(formKey)` 一份）：

| 行 | 内容 | G2 | G3 |
|---|---|---|---|
| ① 身份行 | 头像圈 + 名字 + 徽章 + 键/盘/设 | ✓ | ✓ |
| ② 角色条 | 在场少女横滑 chips（上限 10） | **空**（`:empty` 隐藏） | ✓ |
| ③ 主体切换 | 两枚等宽 pill：`当前少女名` / `主角名` | ✓ | ✓ |
| ④ 数值条 | 6 条（角色：体力/气力/法力/酒/精/理性；主角：体力/气力/法力/TSP/精/运势） | ✓ | ✓ |
| ⑤ 详情抽屉 | 角色：好感度 chips + Palam 网格；主角：主角 chips + M2 备注 | ✓ | ✓ |
| ⑥ 「▼ 状态详情」入口 | 展开/收起 ⑤ | ✓ | ✓ |

**主体切换（本次新增）**：
- 两枚 pill 的**标签直接写名字**（G2：`绀野琳` / `清`；G3：`白莲` / `昂`），玩家一眼知道切给谁，不需要「角色/主角」这种抽象词。
- 默认主体 = **当前少女**（角色交互的主视角是眼前这个人）；主角是次视角。
- 切到主角时：头像圈转黄、数值条换主角的 6 条、抽屉换主角 chips；**角色条与立绘保持可见但不高亮**（在场事实不因看谁而改变）。
- 点角色条任一少女 → 主体**自动切回该少女**（一次点击完成「选人 + 看她的状态」）。
- 主体与选中下标存在 `ShellState` 的壳层状态（每形态独立），**不落盘**、**不提交指令**（§0-12）。

**M1 与 M2 的分工**：M1 的两套数值都来自行解析（HUD 数值行 / 主角数值行），主角抽屉只列屏行可解析项；主角专属详情（素质・经验・装备）属 M2 的 VM 快照。

**高度联动（实测）**：抽屉展开时自动收①②⑥以外的「④数值条」（摘要让位给详情），并让立绘舞台让位；三态正文分别 44% / 43% / 30%，均 ≥30%（§5.1b）。

#### 3.6.2 角色条 `CharacterRail`（G3 专有，G2 留空）

- 数据：M1 = HUD 行解析出的角色块列表（`[名字]` 行 + 紧随的 `好感度`/数值行 → 一个角色块）。解析不出 → 角色条整体隐藏，退回 G2 外观（**不显示空条**）。
- 形态：横滑 pill 行，每枚 = 头像圈（名字首字，M2 换真头像）+ 名字 + 状态点（红 = 危险/发情前日、绿 = 常态；从 HUD 的 `受孕 ○`/`危险日前` 取，取不到就不画点）。
- 上限 **10**：与原版立绘上限一致；超出（理论上不会）显示 `+N`。10 枚在小屏必须横滑，**不换行**（换行会吃掉正文高度）。
- 交互：点击 = 「选中该少女」+「主体切回角色」，两件事一次完成；**绝不提交任何指令**（§0-12）。
- 换对象引导：角色条不放换对象按钮；`变更对象[802]` 就在指令盘系统组里按屏行原序出现（不特殊置顶——位置由语料决定）。

#### 3.6.3 立绘舞台 `SpriteStage`（M1 = canvas 流内；M2 = 独立舞台）

**分期边界必须说清（防误做）**：
- **M1**：立绘仍在正文 canvas 流内渲染——render 已实现立绘图片行几何（BOARD 2026-10-26），壳层**不碰**。多张时 canvas 会按列宽折行、可滚动。壳层只在正文与指令盘之间提供**折叠态标题条**（`立绘 N/10`），让玩家知道有几张、可滚动查看。**M1 不做图片裁剪/重排**（那需要 render 暴露 sprite 矩形，属 M2）。
- **M2（目标形态）**：独立横滑舞台。壳层从 render 拿到每张 sprite 的矩形（新增只读接口，跨模块另波），按人数自适应排布：

| 在场人数 | 单张宽度 | 同屏可见 | 排布 |
|---|---|---|---|
| 1 | 190dp 或 60% 屏宽（取小） | 1 | 居中 |
| 2 | 138dp | 2 | 并排 |
| 3 | 108dp | 3 | 并排 |
| 4 | 92dp | 4 | 并排 |
| 5~6 | 84dp | 4~5 | 横滑 |
| 7~10 | 76dp | 5 | 横滑 |

（数值 = 原型实测宽度，屏宽 390dp 下的自然值；Compose 侧写成 `when (count)` 常量表，不引入比例计算。）

- **可折叠**：舞台标题条右侧一枚「收起 ▾ / 展开 ▸」，折叠后只留一行标题（约 22dp），把空间还给正文。折叠状态记进 `UiPrefs.spriteStageCollapsed`（**跨屏记忆**：玩家既然想看文字，就别每屏弹回来）。
- 点立绘 = 同角色条，只切显示上下文。

#### 3.6.4 小屏压力实测（390 / 360 屏宽，10 人）

| 分区 | 390×844（10 人，收起） | 390×844（10 人，**指令盘展开**） | 360×740（10 人，收起） | 360×740（立绘折叠） | 360×740（**展开 + 舞台让位**） |
|---|---|---|---|---|---|
| HUD（含角色条 + 双行数值） | 28% | 28% | 28% | 28% | 28% |
| 正文 | 46% | **32%** | **34%** | **44%** | **35%** |
| 立绘舞台 | 12% | 0%（让位） | 14% | 4%（仅标题条） | 0%（让位） |
| 指令盘 | 12% | 44% | 12% | 12% | **38%**（s 档上限 40%） |

（读数 = 原型实测，2026-10-27；`s` 档上限 40% 就是为小屏把正文从 29% 拉回 35% 而设。）

⇒ **结论**：
1. 收起态正文 ≥34%，折叠立绘可到 44%；
2. 展开态正文 32~35%（≥30% 基线），代价由「立绘舞台让位」支付；
3. **两个高度旋钮都不许用视口单位**（§0-14），否则会把收起按钮顶出屏外，症状是「无法收起」。

#### 3.6.5 详情抽屉（随主体切换）

- 标题 = `▼ 当前主体名　好感度 / Palam`（主体为少女）或 `▼ 主角名　主角状态`（主体为主角）。
- 少女：经验 chips（好感度/信赖度/欲求不满度/孩子个数/受孕/战斗能力…）+ Palam 网格。
- 主角：主角 chips（清醒裾裾/今日运势/危险日前/理性…）+「主角专属详情属 M2」备注。
- 切换主体或选中少女**不重解析**：一次解析出全部角色块与主角块，切换只是选 index（纯壳层状态）。
- 解析不到 Palam → 抽屉只显示经验 chips；连经验也没有 → 抽屉入口隐藏。

## 4. 分区详细规格

### 4.1 顶部状态 HUD（新建 `PortraitHud.kt`）

**按形态分级**（§3.5）：G0/G1 = 徽章级（名字行放日期/所持金/地点徽章、buff 行整行变 chips、数值条保留，**无 Palam 抽屉**——交互对象不存在，抽屉按钮也不显示）；**G2/G3 = 统一 HUD**（同一套骨架，规格见 §3.6.1：数值条 + 主体切换 + Palam 抽屉；G3 只多一条角色条）。分级显隐属「数据失配即隐藏」的同族降级：G2/G3 判据成立但 Palam 行解析不到 → 抽屉按钮隐藏，不显示空抽屉。

- **① 身份行**：头像圈（36dp，名字首字；主体=主角时转黄）+ 名字行（名字 + 徽章 chips）+ 右侧三枚 34dp 图标钮（键盘 `InputToggle` 现有 / 指令盘开关 / 设置）。
- **② 角色条**（仅 G3）：横滑 chips，见 §3.6.2。
- **③ 主体切换**（仅 G2/G3）：两枚等宽 pill，标签 = 当前少女名 / 主角名，当前主体高亮。规格与交互见 §3.6.1。
- **④ 数值条**：3~6 条/行（断点 §5），每条 = 标签 + 等宽数值 + 4px 圆角条。角色主体 6 条（体力/气力/法力/酒/精/理性），主角主体 6 条（体力/气力/法力/TSP/精/运势）。条色见 §11。
- **⑤ 详情抽屉 + ⑥ 入口**：见 §3.6.5；展开时 ④ 自动收起（摘要让位详情）、立绘舞台让位，正文保持 ≥30%。
- HUD 整体 `background #161616`、底部 14dp 圆角、`safeDrawingPadding()` 顶部吃挖孔（`ShellUi.kt:326` 同口径——竖屏挖孔在顶部）。
- HUD 高度预算：G0/G1 收起态 ≤ 112dp；G2/G3 收起态 ≈ 21% 屏高、抽屉展开 ≈ 41%（数值条已让位），**任何状态不遮正文交互区**（分区不浮层，沿用 `ShellUi.kt:270-271` 定调）。

### 4.2 正文控制台（零改动 + 一个装配参数）

- `CanvasConsoleView` 原样 `AndroidView` 嵌入（`MainActivity.kt:202-206` 现状）。
- 唯一变化：`fontColumnsOverride` 的取值 = **按当前方向选档**（§6/§7）：横屏用现有 `fontColumns`，竖屏用 `fontColumnsPortrait`（缺省 62）。`screenFitEnabled` 语义不变（true=适应屏幕，false=固定列）。
- **禁止**在 View 外包 Compose 滚动——canvas 自带滚动/手势（`attachGestures`，`MainActivity.kt:207`），套二层手势必炸。

### 4.3 底部指令盘（新建 `CommandTray.kt`）

- 数据：`state.chips`（现有 250ms 扫描快照）→ `railRowsOf` 按屏行分行 → `OptionChipButton` 渲染。**不排序、不跨行合并、不按指令号自行分组**（`ShellUi.kt:370-373` 用户定调原文：按游戏显示行分行）。
- **组标签 ≠ 分组**：`【主菜单】/【系统菜单】/【Act_COM】这类组头来自**游戏自己的屏行文本**（§3.5 的 `【…】` 剥取），渲染成组头上方的 10sp 绿字标签行；剥不出就没有标签行，按钮仍按屏行原序平铺。**我们永不发明分组**——与防眼瞎 #4 同源。
- **展开默认随形态**（§3.5）：G0 自动展开；G1/G2/G3 peek 收起。
- **展开态高度上限 = 手机内容区高度的百分比，不是视口单位**：`.ep-tray { max-height: 46% }`（`s` 档 40%），`.ep-cmds` 在内部滚动（`flex: 1 1 auto; min-height: 0; overflow-y: auto`），**收起按钮恒在屏内**。Compose 对应 `BoxWithConstraints` 取 `maxHeight` 后 `Modifier.heightIn(max = maxHeight * 0.46f)`；**禁止** `fillMaxHeight(0.34f)` 之于 window 高度、也禁止任何 `vh` 类视口单位。
- **展开时立绘舞台自动让位**：`.ep-form.tray-expanded [data-stripwrap] { display: none }`——两者抢同一块高度，选指令时文字优先；收起指令后舞台恢复（用户自己的折叠偏好不被改写）。
- **收起态（G1/G2 默认）**：上下文行（执行中 chip + 上回指令，M1 行解析、失配隐藏）+ peek = 第一屏行（≤4 枚，`OptionRailRow` 现有溢出横滚逻辑）+ 「更多指令 ▾」整行按钮。
- **展开态**：全部屏行分组纵排（含组标签行），外层纵向滚动；「收起到常用指令 ▴」收起。G1/G2 的用户手动开合记忆到 `UiPrefs.commandTrayOpen`（§7），G0 的自动展开不受该键影响。
- 按钮 min-height 34dp、2~4 列网格（断点 §5）；系统类按钮（无 `[数字]` 编号的候选）用 ghost 样式（§11），**判定 = 候选 label 不含 `[数字]` 尾缀**，不做白名单。
- 指令盘整体高度计入正文分区（Column weight 分配），**不浮层覆盖正文**。

### 4.4 输入条 / 抓手 / 长按提示（全部沿用）

- 唤出：右上键盘图标 / 底边抓手（位置偏好 `inputKnobFraction` 现有）；收起：抓手拖下 / 点画面 / 提交成功 / 15s 静置（有焦点不收）。全部逻辑在 `ShellUi.kt:300-320`、`MainActivity.attachGestures`，**一行不改**。
- 宏条只在输入条展开时显示（`ShellUi.kt:425-456` 现状）。
- 长按候选 → `ButtonTooltipOverlay`（`ShellUi.kt:507-541`），竖屏卡片宽度 `fillMaxWidth(0.92f)` 与现值一致。

### 4.5 加载 / 失败覆盖层（零改动）

`LoadingOverlay`/`FailureOverlay` 横竖屏共用，竖屏 `BoxWithConstraints` 已在设置页验证过响应式套路（BOARD 2026-10-23），本波不碰它们。

## 5. 自适配规格

### 5.1 断点（纯函数，放 `PortraitGrid.kt`，单测钉死）

输入 = 竖屏正文区**屏宽 dp**（`BoxWithConstraints.maxWidth`，与设置页响应式同套路）：

| 档 | 屏宽 dp | HUD 条/行 | 指令盘列数 | 抽屉 Palam 列/行 |
|---|---|---|---|---|
| s | < 380 | 3 | 2 | 2 |
| m | 380–519 | 3 | 3 | 3 |
| l | 520–639 | 6 | 3 | 4 |
| xl | ≥ 640 | 6 | 4 | 4 |

（原型 JS 的 `sizeClass/cmdCols/hudCols/palamCols` 原样搬 Kotlin；数值以原型为验收基准。）

多角色页的**双行数值**在 s/m 档每行 4 条迷你条（体/气/法/酒，精并入详情），l/xl 档每行 5 条（含精）；**立绘宽度**不跟断点、只跟在场人数（§3.6.3 常量表，避免两套变量打架）。

### 5.1b 竖屏分区高度预算（验收基线，§3.6.4 同源）

| 分区 | 常态（收起） | 10 人多角色（收起） | 立绘折叠 | 指令盘展开 | 状态详情展开 |
|---|---|---|---|---|---|
| HUD | 18~28% | 21~28% | 21~28% | 21~28% | **41%**（数值条让位） |
| 正文 | ≥ 45% | 44% | 44% | 30~35% | **43%** |
| 立绘舞台 | — | 12~18% | 4% | 0%（让位） | 0%（让位） |
| 指令盘 | ≤ 19% | 12% | 12% | 38~44%（上限 46%，s 档 40%） | 12% |

（读数 = 原型实测 2026-10-27，G3/390×844/2 人。）

正文区在**任何形态任何开合态**下不得低于 30% 屏高（低于 30% 即按 §10-11 走降级旋钮）。当前三态实测 44% / 30% / 43%，均为「让位换空间」的结果，不是靠缩字号。

### 5.2 竖屏字号档位（逻辑列宽）

新档位表：**50（特大）/ 62（大，缺省）/ 75（标准）/ 90（小）**。机制与横屏档位完全同构：`fontColumnsOverride` 构造期传入 → `GameSession.consoleWidth`（`GameHost.kt:1148`）→ 改档 `recreate()`（`MainActivity.kt:257`）。

换算公式（**复用 `ScreenLayout.fixedColumns`，禁止重写**）：`font = widthPx / (columns × 0.52 + 1/6 + 0.03)`（`CELL_PIXEL_FACTOR=1.04` 出处 `StringMeasure.cs:37`；行高比 19/18 出处 `ConfigData.cs:66-67`）。竖屏算例（widthPx = 短边物理像素）：

| 设备（devices.yaml 档案） | 竖屏宽 px | 50 列 | **62 列（缺省）** | 75 列 | 90 列 | 对照：横屏 110 列 |
|---|---|---|---|---|---|---|
| iqoo-neo6se 2400×1080@400 | 1080 | 41px | **33px** | 28px | 23px | 42px（UP3 实测 ✓） |
| S24U 3120×1440@500 | 1440 | 55px | **44px** | 37px | 31px | 54px（UP3 实测 ✓） |
| redmi-13c 1600×720@260 | 720 | 28px | **22px** | 18px | 15px | 28px（UP3 实测 ✓） |

（公式对拍：横屏 110 列三台设备的计算值与 UP3 真机实测逐值一致，说明换算无误。dp = px ÷ (densityDpi/160)。62 列在三台上 ≈ 13~14dp 汉字，与横屏 110 列的 15~17dp 同档可读。）

- `screenFit=true`（适应屏幕，缺省）时：竖屏 fit 模式列数下限仍是 `minColumns` 保底 84（`ScreenLayout.fit` KDoc）→ 竖屏字号 ≈ 84 列档。**允许**，用户要更大字就关适应屏幕或调档——与横屏语义一致，不加新概念。
- 旋转时逻辑列宽**不变**（构造期定死），fit 模式字号随可见区重推（`CanvasConsoleView` 三推导点已收 `ScreenLayout`，UP3）——「旋转不打断脚本」语义保留。

### 5.3 安全区

竖屏挖孔/刘海在顶部：HUD 顶 padding 吃 `safeDrawingPadding()` 顶部 inset；输入条/抓手底部吃导航条 inset（adjustResize + 现有 `safeDrawingPadding`，`ShellUi.kt:326`）。原型里的「刘海开关」仅演示 ±34px padding。

## 10. 风险与已知坑（逐条写进契约「卡点」栏）

1. **行解析脆性**：HUD M1 解析锚定「行首标签」，语料改版式会漂——防线 = 失配即隐藏 + 解析器纯函数单测钉样例；不许 try-catch 兜底成默认值。
2. **62 列下脚本版式与 PC 分叉**：eraTW 原生支持窗口宽度变化（原版语义），但个别脚本可能按宽列排版——竖屏验收必须实际玩到「能力显示/Act_COM/地图」三类屏各一次，发现排版崩坏登记不硬修（ADR-005：官方 bug 原样复刻的原则同样适用于官方「窄窗口下的排版」）。
3. **旋转 × 档位交互**：固定列模式旋转后字号随屏宽缩放（同列数），fit 模式列数重推——两种行为都写进用户文档口径，不算 bug。
4. **指令盘 250ms 扫描抖动**：右 rail 有「闪烁收口」前科（`ShellUi.kt:357-360`）——指令盘的**收起/展开只跟用户开关**，不跟 chips 是否为空；空 chips 时显示占位行「（本屏没有可点选项）」，不隐藏整个盘。
5. **`requestedOrientation` 运行期切换**：TODO(verify)（模拟器 API34 验证：切偏好后立即生效、不闪屏、不重建）。
6. **app 模块单测基建**：app 现在只有 androidTest（`app/src/androidTest/**`），`src/test` 纯 JVM 源集未用过——TODO(verify) 第一条用例先跑通基建再铺量；若 AGP 配置有障碍，纯函数下沉到 `render` 模块旁路（需组长接线，因为跨了模块所有权）。
7. **HUD 图标钮与现有 `SpiralToggle` 语义冲突**：竖屏「指令盘开关」复用螺旋图标的视觉但行为不同（横屏=右 rail 滑入滑出，竖屏=指令盘展开收起）——实现时拆成两个 Composable 共用画法，不共用状态。
8. **三形态判据的边界情形**（§3.5）：存档页 8~16 钮落 G1、训练页无 3xx 也落 G1——**都是可接受摆法**，不要为了「更准」引入语义正则或 VM 变量查询。真出现摆法难受的屏，登记到 BOARD 由用户定调，不自行加判据。
9. **组标签剥取依赖语料写法**：`【主菜单】` 全角括号是语料约定，不是引擎契约。剥不出就退化成无标签平铺（已设计成降级路径），**不许**把标签集合写进白名单去「保证显示」。
10. **G0 自动展开的高度风险**：主菜单 27 钮在小屏（360×740）上展开会占掉大量正文。防线 = 展开区上限 34% 屏高 + 内部滚动（§4.3）；实测若提示行被挤没，把 G0 上限降到 28% 并记录读数，不要改成自动收起（那会让玩家多点一次）。
11. **多角色时正文被压到 34%（小屏 10 人，§3.6.4 实测）**：立绘折叠是唯一逃生口（→44%）。若真机仍不可用，下一档旋钮 = 把 HUD 的 chips 行并入详情抽屉（再省 ~6%）；**不要**动字号档——它改的是逻辑列宽，会连带改变脚本版面与行折，属于语义面。
12. **角色块解析的脆性比 HUD 数值更高**：它决定 G2/G3 分流与角色条长度。判据必须「同一角色块内数值行紧跟名字行」，缺一条就当该块不存在；解析出的角色数 < 2 时**降级回 G2**（宁可少一条角色条，不要显示错的人名列表）。
13. **`变更对象[802]` 只当作存在性判据，不当作可编程接口**：壳层不得用 802 的编号去拼提交值（原版它的实参形态未取证，属 TODO(verify)）。M1 只保证它在指令盘里可点。
14. **立绘上限 10 的可读性下限**：10 人 × 76dp 在 360 屏上只能同屏 4~5 张（其余横滑）。这不是缺陷而是取舍；验收以「能滑到第 10 张且名字可见」为准，不以「一屏全见」为准。
15. **指令盘展开后收起按钮必须恒在屏内**（2026-10-27 用户报「无法收起」）：这是 §0-14/15 两条的合成症状——`vh` 让展开区过大 + 框内可滚动把按钮顶出去。验收硬项：**四种形态 × 收起/展开 × 390/360 两档宽，收起按钮的 rect 必须完整落在手机内容区内**（可写成 UI 测试断言 `toggle.bottom <= screen.bottom`）。
16. **HUD 顶部不可被裁**：同一根因的第二症状（隐藏输入条的 transform 撑大 scrollable overflow ⇒ 框内自动滚动）。验收硬项：任意交互后 `screen.scrollTop == 0` 且 HUD 顶部 ≥ 内容区顶部。

1. 在场角色行 = 一行里出现 **≥2 个 `[名字]` 方括号 token**（`[同行中]` 这类状态词不是名字 → 用「方括号内不含状态词表」排除；状态词表最小集：同行中/战斗不能/睡眠/发情）。
2. 一个角色块 = 「`[名字]` 行」+ 其后的「`[名字] 好感度…` 行」+「`名字 [体力] …` 数值行」，**三行必须名字一致**；缺任一行 → 该块不计入（§10-12）。
3. 主角块 = 数值行标签为解析出的主角名（`(主角)` 前缀行给出）或 HUD 名字；主角**不计入**角色条。
4. 角色数 = 合格块数；`< 2` → G2（单人）外观；`≥ 2` → G3。
5. `受孕 ○/×`、`危险日前` 从该块的状态行取，取不到则角色条不画状态点。

**解析规则（三条，缺一不可）**
1. **锚行首标签**，不锚列位（逻辑列宽随档位变，同一行会折）。标签集合固定：体力/气力/法力/酒/精/精力/TSP/清醒裾裾/好感度/信赖度/欲求不满度/孩子个数/怀孕/工作地点/战斗能力/执行中/上回指令/buff 括号族/组标签 `【…】`。
2. **数值取标签后首个整数 token**；分母式 `a/ b` 取双值（`3249/ 3845` 的 b 是上限）；`Ex 113791`/`S 3330` 取字母后的整数；`87%` 去 `%`。
3. **任何一条不成立 → 该字段 null → 壳层隐藏该控件**（绝不显示编造值、绝不显示 0 兜底）。负样例：全角数字 `３８４５`、标签在行中不在行首、标签后无数字、`执行中:` 后无引号内容 → 全 null。
